# ROADMAP — развитие функционала бота

Рабочий план по фазам. Двигаемся последовательно, каждая фаза — отдельная сессия разработки. Не начинать следующую фазу, пока предыдущая не закрыта и не проверена руками.

**Принцип, зафиксированный по итогам обсуждения:** бот фиксирует значения (еда, вес, шаги, вода). Он не советует, не корректирует цели сам и не различает дни по типу активности. Любая функция, которая начинает «решать за пользователя» или «учить» — вне периметра этого проекта на данном этапе.

**Mini App — основной интерфейс.** Любая новая функция по умолчанию получает UI в Mini App в рамках той же фазы, а не отдельным довеском после. Бот-команда — дополнительный, не единственный способ доступа. Acceptance каждой фазы включает проверку в Mini App, а не только через команду бота.

**Контекст, важный для Фаз 4–5:** собираемые данные будут отдаваться внешнему специалисту (диетолог + тренер) для оценки и построения графика питания/тренировок вперёд. Значит: (а) история не должна искажаться задним числом (Фаза 4), (б) выгрузка должна быть максимально подробной, а не только сводной (Фаза 5) — экономить на детализации здесь не нужно.

## Вне периметра (сознательно не делаем)

| Идея | Почему нет |
|---|---|
| Разные таргеты КБЖУ на тренировочные/дни отдыха | Это уже логика коуча, а не трекера. Пользователь сам знает свой день — бот просто пишет цифры |
| Авто-детектор плато / авто-предложение поднять калораж | Тоже коучинг. Решение о смене таргета — целиком на пользователе (см. Фазу 3 — ручная корректировка) |
| Персонализация расписания scheduler.js под график каждого юзера (сейчас жёстко MSK, один сценарий на всех) | Низкий приоритет, не связано с фиксацией данных. Отложено — вернёмся, если станет реальной болью на нескольких пользователях |
| Полноценный трекер тренировок (подходы/веса/прогрессия) | Отдельный домен, не относится к «food tracker» |

## Фаза 1 — Редактируемый журнал веса

**Проблема:** `users.weight_kg` пишется один раз при онбординге и потом не обновляется никогда (кроме полного `/reset`, который стирает весь профиль).

**Решение:**
- Новая таблица `weight_logs` (`telegram_id`, `log_date`, `weight_kg`, `logged_at`) — по образцу `water_logs`.
- Команда `/вес 89.4` (алиас `/weight`) — пишет запись на сегодня. Если на сегодня уже есть запись — перезаписывает (а не дублирует).
- `/вес` без числа — показывает последнюю записанную цифру и дату.
- При каждой записи — синхронно обновлять `users.weight_kg` (последнее известное значение), чтобы `/profile` показывал актуальный вес без доп. JOIN.
- Миграция: `migration_weight_log.sql`.

**Acceptance:**
- Можно записать вес в любой день, поверх старого значения того же дня.
- `/profile` показывает вес из последней записи, а не из онбординга.
- История сохраняется по датам (нужна для Фазы 4 — выгрузки).
- Тот же функционал доступен в Mini App: карточка «Вес» рядом с водой — редактируемая для сегодня, read-only при просмотре прошлых дней (или «не записан», если записи не было).

## Фаза 2 — Шаги (ручной ввод)

**Решение:**
- Новая таблица `steps_logs` (`telegram_id`, `log_date`, `steps`) — одно значение в день, перезаписывается при повторном вводе (не суммируется, в отличие от воды).
- Команда `/steps 8500` (ASCII-имя, тот же урок из бага с `/вес`) — записывает/обновляет шаги за сегодня. `/steps` без числа — показывает сегодняшнее значение.
- Карточка «Шаги» в Mini App рядом с весом — редактируемая для сегодня (поле ввода + «Сохранить», как у веса), read-only при просмотре прошлых дней.
- Миграция: `migration_steps_log.sql` (можно объединить с Фазой 1 в один файл — решим при реализации).

**Acceptance:**
- Значение шагов за день можно вводить и перезаписывать вручную — и через бота, и через Mini App.
- Данные доступны для выгрузки (Фаза 5).
- ✅ Готово: `/steps` в боте + карточка «Шаги» в Mini App (та же схема, что у веса — редактируемая сегодня, read-only в истории).

## Фаза 3 — Ручная корректировка дневных целей (БЖУ/калории)

**Проблема:** изменить `daily_calories/daily_protein_g/daily_fat_g/daily_carbs_g` сейчас можно только через `/reset` — а это полный 8-шаговый опрос заново (пол, возраст, рост, вес, активность, цель), даже если нужно поправить только сами цифры БЖУ.

**Решение:**
- Новая команда `/targets` (ASCII-имя — см. урок из бага с `/вес`: Telegram не распознаёт кириллические команды как `bot_command` и не даёт зарегистрировать их в `setMyCommands`; кириллический алиас можно оставить вторым, необязательным вариантом).
- `/targets 2000 175 70 180` — напрямую перезаписывает калории/белки/жиры/углеводы в `users`, минуя `calculateTDEE`/`calculateMacros` (это ручной ввод, не пересчёт по формуле).
- `/targets` без аргументов — показывает текущие цифры.
- Валидация — разумные границы значений (не ноль, не абсурдные числа), без дополнительной логики поверх.

**Важно — связь с Фазой 4:** сейчас цель менялась только через редкий `/reset`, поэтому баг «смена цели переписывает историю задним числом» был малозаметен. С этой командой менять цель станет намного проще и чаще — баг станет ощутимым быстрее. Делать Фазу 4 сразу следом за этой, не откладывать.

**Acceptance:**
- Калораж/БЖУ можно поменять одной командой, без прохождения анкеты заново.
- `/profile` и Mini App сразу показывают новые цифры.
- Кириллический алиас, если добавлен, — не единственный и не рекламируемый способ вызова.
- ✅ Готово: `/targets` в боте + модал «Цели на день» в Mini App (кнопка «✏️ ЦЕЛИ» рядом с макронутриентами, доступна только для сегодняшнего дня).

## Фаза 4 — Фикс: смена цели не должна переписывать историю

**Проблема:** `buildTotalsText()` (`src/bot/handlers/food.js:69-135`) и `eveningSummary()` (`src/services/scheduler.js:134-196`) на каждый запрос берут `daily_calories/protein/fat/carbs` из ТЕКУЩЕЙ строки `users`. Если пользователь позже меняет цель (`/reset` или будущий `/profile edit`), все прошлые дни в Mini App и в отчётах молча пересчитываются под новую цель — история искажается задним числом.

**Решение (реализовано):**
- Новая таблица `daily_targets(telegram_id, log_date, calories, protein_g, fat_g, carbs_g)`, `UNIQUE(telegram_id, log_date)`.
- Снапшот пишется в `eveningSummary()` (`src/services/scheduler.js`) — джобе 23:00 MSK, последней за день, для всех активных пользователей разом (не только тех, кто логировал), одним batched `upsert`. Отдельный cron не понадобился — job уже итерируется по всем юзерам ежедневно.
- «Сегодня» (`buildTotalsText` в `food.js`, `/api/today/:userId`) как и раньше читает live-профиль — цель ещё не «закрыта», это осознанно не менялось.
- Только исторический эндпоинт `/api/logs/:userId/:date` (`index.js`) подмешивает снапшот из `daily_targets` вместо live-полей `users`, с фолбэком на live-профиль, если снапшота ещё нет (день до появления таблицы).
- Mini App (`app.js`) правок не потребовал — он и так просто рендерит то, что вернул API.
- Миграция: `migration_daily_targets.sql`.

**Acceptance:**
- ✅ Меняем цель в профиле → открываем прошлый день в Mini App → проценты/остатки считаются от таргета, который действовал в ТОТ день (по снапшоту 23:00), а не от нового.
- Это не только внутренняя целостность данных — на этом снапшоте строится Фаза 5 (выгрузка для специалиста): без него отчёт за прошлые дни показывал бы не те цели, что реально действовали.
- Известный компромисс: если цель поменяли уже после 23:00 в тот же календарный день, снапшот за этот день зафиксирован со старым значением. Не фиксили специально — редкий край, не стоит усложнения.

## Фаза 5 — Еженедельная выгрузка статистики (максимально подробная)

**Контекст:** отчёт будут читать диетолог и тренер, а не только сам пользователь — на основе него будут корректировать питание и тренировки вперёд. Экономить на детализации нельзя: сводных цифр «за неделю» недостаточно, нужен разбор по каждому приёму пищи.

**Решение (реализовано):**
- `src/services/export.js` — `generateWeeklyReport(telegramId)`, единственный генератор отчёта, используется и ботом, и API.
- Команда `/week` (ASCII-имя, тот же урок из бага с `/вес`) — собирает данные за последние 7 календарных дней (MSK, сегодня включительно), отправляет `.md` как документ (`ctx.replyWithDocument`).
- `GET /api/export/week/:userId` — тот же генератор, отдаёт файл с `Content-Disposition: attachment`. Кнопка «📄 Скачать отчёт за 7 дней» в Mini App (статичная, не завязана на выбранный в таймлайне день) скачивает через Blob + временную ссылку — имя файла считает сама на клиенте той же логикой дат, не полагаясь на чтение заголовка кросс-доменно.

**Предусловие (реализовано):** для разбивки по приёмам пищи нужен `meal_type` в `food_logs` — поле существовало в схеме, но `insertLog()` (`src/bot/handlers/food.js`) никогда его не передавало, всегда падало в дефолт `'snack'`. Сделали частью Фазы 5 (не отдельной опциональной фазой, как было раньше) — `mealTypeForHour()` определяет `breakfast/lunch/dinner/snack` по часу лога (MSK, через новый `nowMSK()` в `time.js`), без ИИ и без вопроса пользователю.

**Содержимое файла — по каждому из 7 дней:**
- Дата, день недели
- Калории: факт / цель / % выполнения (цель — из снапшота Фазы 4, не из текущего профиля)
- Белки / жиры / углеводы: факт / цель, каждый отдельно
- Полный список приёмов пищи за день — время, название, ккал, БЖУ, `meal_type` (не только сумма — весь журнал целиком, чтобы было видно реальное распределение по времени и приёмам)
- Вода за день (сумма `water_logs`)
- Вес (если есть запись)
- Шаги (если есть запись)

**Итоги за неделю:**
- Среднее и суммарное по калориям и по каждому макросу
- % дней с выполненной нормой калорий
- Изменение веса за период (последняя запись минус первая, если обе есть) + мин/макс за неделю
- Среднее по шагам, среднее по воде
- Дни без данных — явно помечены «нет данных», не подставляются нули (тот же принцип, что уже используется в `eveningSummary` для нулевого дня)

**Acceptance:**
- ✅ Работает даже если веса/шагов/воды не было ни разу — помечает как «нет данных», не падает.
- ✅ Файл — чистый текст, без HTML-тегов и без Markdown-мусора.
- ✅ Отчёт идентичен и через `/week`, и через кнопку в Mini App — один и тот же `generateWeeklyReport()`.
- Метрика «% дней с выполненной нормой» считает день выполненным при 95–110% от цели (та же граница, что и в `eveningSummary`).
